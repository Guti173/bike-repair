# Bike Repair Management — Specification
## Goal
Build a small local prototype for a bicycle repair shop.

The application must allow workshop staff to:

1. Create a repair order.
2. View existing repair orders.
3. Change the status of a repair order.

The goal is to provide a simple, understandable and reliable workflow rather
than a feature-rich product.

## Scope

### Required features

A repair order contains:

- `id`: unique identifier generated by the application.
- `customer_code`: fictitious customer identifier.
- `bicycle_description`: short description of the bicycle.
- `reported_issue`: problem reported by the customer.
- `status`: current repair status.

Allowed statuses:

- `pending`
- `in_progress`
- `completed`

The user must be able to:

- Create a repair order.
- List all repair orders.
- Change the status of an existing repair order.

## Data validation

The backend is responsible for validating all input.

Suggested limits:

- `customer_code`: 1–40 characters.
- `bicycle_description`: 1–200 characters.
- `reported_issue`: 1–500 characters.

Unexpected fields should be rejected.

## Persistence

Repair orders will be stored locally using SQLite.

No cloud services or external databases are required.

## Privacy constraints

Only synthetic data may be used.

The prototype must not store:

- customer names;
- phone numbers;
- email addresses;
- postal addresses;
- payment information;
- any other real personal data.

`customer_code` is an invented identifier and must not contain personal
information.

Request bodies or repair descriptions should not be written to application
logs unnecessarily.

No secrets, credentials or environment files containing secrets may be
committed to the repository.

## Future customer data

If the product later required customer contact information, customer identity
data should be stored separately from repair information.

Repair orders would reference an internal customer identifier instead of
duplicating contact data.

Access to personal data should follow least-privilege principles. Employees
who only need repair information should not automatically have access to
customer contact information.

Authentication, authorization, audit logging, retention policies and
appropriate encryption would be considered before introducing personal data.

## Out of scope

The following are intentionally excluded from this prototype:

- Authentication and user accounts.
- Real customer personal data.
- Roles and permissions.
- Notifications.
- Payments.
- Inventory management.
- Cloud deployment.
- AI features inside the product.
- Advanced search or filtering.
- Production-ready infrastructure.

## Technical approach

### Backend

- Python
- FastAPI
- SQLite
- Pydantic validation
- Automated tests with pytest

### Frontend

- React
- TypeScript
- Vite

The user interface will be in Spanish because the fictional end user is a
Spanish bicycle workshop.

Source code will be written in English.

## API

Minimum API surface:

### `POST /repair-orders`

Create a repair order.

### `GET /repair-orders`

Return all repair orders.

### `PATCH /repair-orders/{id}/status`

Change the status of an existing repair order.

## Acceptance criteria

The prototype is considered complete when:

1. A valid repair order can be created from the UI.
2. Created repair orders remain available after restarting the backend.
3. Existing repair orders are displayed in the UI.
4. A repair order can move between the three allowed statuses.
5. Invalid status values are rejected by the backend.
6. Empty or invalid required fields are rejected.
7. Unexpected input fields are rejected.
8. Core backend behaviour is covered by automated tests.
9. No real personal data, credentials or secrets are present in the repository.
10. The application can be started using instructions in the README.
