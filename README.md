# Bike Repair Management Backend

Local prototype using FastAPI, Pydantic and Python's built-in SQLite support.
Requires Python 3.10 or newer. Only the backend is implemented.

## Install

Run from the repository root:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

## Run

```sh
python -m uvicorn backend.main:create_app --factory --host 127.0.0.1 --port 8000
```

Interactive API documentation is available at <http://127.0.0.1:8000/docs>.
The backend creates `repair_orders.sqlite3` in the repository root on startup.
Orders persist across restarts. This runtime database is ignored by Git.

## API

| Method | Path | Behavior |
| --- | --- | --- |
| POST | `/repair-orders` | Create an order; return `201`. |
| GET | `/repair-orders` | List all orders by ascending ID; return `200`. |
| PATCH | `/repair-orders/{id}/status` | Update status; return `200` or `404` if absent. |

Creation accepts only `customer_code` (1–40 characters),
`bicycle_description` (1–200), and `reported_issue` (1–500).
Surrounding whitespace is removed before length validation.
IDs are generated by SQLite; new orders always start as `pending`.

Status updates accept only `status`: `pending`, `in_progress`, or `completed`.
Surrounding whitespace is removed. Any transition between these statuses,
including retaining the current status, is allowed. IDs must be integers within
SQLite's signed 64-bit range.
Invalid input, missing required fields, and unexpected fields return `422`
through FastAPI/Pydantic validation.

Use synthetic data only. Do not submit real customer details or secrets.
The application does not log request bodies or repair descriptions.

## Test

```sh
python -m pytest -q
```

Tests use pytest temporary SQLite files through `create_app(database_path)`.
They do not access the local runtime database. Persistence is checked by
restarting the app against the same temporary database.
